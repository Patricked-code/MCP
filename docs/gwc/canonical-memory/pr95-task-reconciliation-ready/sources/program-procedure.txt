WHY THIS PROGRAM EXISTS
The GWC program exists to evolve the existing MCP additively from a set of substantial governed capabilities into one universal, contractual, end-to-end governed execution workflow. The goal is that a newly connected agent can recover context, resolve the target, inherit governance, find existing work, continue the correct governed Task, prove every material transition, resume after interruption, and continue to the next safe executable work without reconstructing a long human prompt.

ARCHITECTURE-FIRST PROCEDURE
1. Observe and map the existing MCP.
2. Define the 73 stable GWC responsibilities and their authorities, evidence, preconditions, postconditions, transitions, replay, concurrency, failure and recovery behavior.
3. Apply existing-first integration: REUSE → WRAP → GENERALIZE → EXTEND → NEW.
4. Consolidate one canonical architecture; historical or deprecated claims remain history and never compete with the canonical body.
5. Produce detailed evolution design and Task Blueprints without promoting them to runtime Tasks.
6. Reconcile every future blueprint against the live Governed Task Queue.
7. Only classification NEW_TASK may create a new runtime Task. CONTINUATION, DUPLICATE, CONFLICT, BLOCKED and OUT_OF_SCOPE must never be converted into duplicate work.
8. Materialize bounded work according to dependencies, priorities, resource scopes and authority boundaries.
9. Execute through governed observation, authorization, minimal locks, tests, review, exact-head merge, exact-SHA deployment proof, terminal verification and closure.
10. Prove universality with GW-73 on a non-MCP target without project-specific hardcodes.

AUTHORITY BOUNDARIES
GWC is an orchestrator of existing authorities, not a new master authority.
Do not create a second Task Queue, Live State, Governed Session engine, Lock Service, GitRegistry, Operational Memory, GitHub Control Plane, deployment authority or runtime authority.
Architecture documentation is not runtime state.
Canonical memory is continuity evidence, not live approval.
GitHub live owns current versioned GitHub facts; runtime and operational facts must be re-observed from their actual authorities.

CURRENT MISSION-SPECIFIC SOURCE RULE
For this canonical-memory placement and verification mission, LOCAL_CLONE_USED = NO.
All versioned repository conclusions are grounded directly in GitHub live refs and exact SHAs.
Future missions must obey their own explicit source rule and may never substitute a local checkout for current GitHub truth.

TASK BLUEPRINT ≠ GOVERNED TASK
A blueprint is a versioned execution specification. It can yield zero, one or several runtime Tasks after live reconciliation. No blueprint becomes a Task merely because it exists in Git.
